07 Python dataclasses

A dataclass is a regular Python class decorated with @dataclass. The decorator inspects the class body for field declarations — lines of the form name: type or name: type = default — and automatically generates an __init__ method that accepts those fields as parameters, a __repr__ that prints all fields, and an __eq__ that compares instances by field values. The result is a clean, self-documenting container class with none of the boilerplate of a hand-written constructor.

Fields without defaults must be listed before fields with defaults, the same rule as positional vs keyword arguments in a function signature. For mutable defaults such as lists or dicts, Python forbids writing tags: list = [] directly — all instances would share the same list object. Instead, field(default_factory=list) tells the dataclass machinery to call list() fresh for each new instance.

from dataclasses import dataclass, field

@dataclass
class Point:
    x:      float                          # required field — no default
    y:      float                          # required field — no default
    label:  str  = "unknown"              # optional field with scalar default
    tags:   list = field(default_factory=list)  # mutable default — use field()

p = Point(1.0, 2.5)
print(p)   # Point(x=1.0, y=2.5, label='unknown', tags=[])
print(p == Point(1.0, 2.5))   # True — __eq__ compares field values
  • 1
    @dataclass — the decorator that triggers code generation; Python inspects the class body and synthesises __init__, __repr__, and __eq__ at class-creation time
  • 2
    x: float — a required field; no default value means the caller must supply it as the first positional argument to Point(...)
  • 3
    label: str = "unknown" — an optional field with a plain immutable default; safe to write directly
  • 4
    field(default_factory=list) — for mutable defaults, field() stores a callable rather than an object; each Point() call gets its own fresh list, avoiding shared-state bugs
In this file

Five dataclasses group related data without boilerplate constructors: PurpleData (three DataFrames from the tar archive), QCData (purity / ploidy / status scalars), MSIData (pre-formatted score and status strings), CNVkitData (three optional DataFrames), and PlotInputs (the top-level aggregator). PlotInputs uses field(default_factory=QCData) and field(default_factory=MSIData) so that callers who omit those fields get safe default instances rather than None.

08 pandas DataFrames and .iterrows()

A DataFrame is pandas' central data structure: a two-dimensional table where each column has a name (taken from the header row of the file) and a consistent dtype. pd.read_csv(path, sep="\t") reads a tab-delimited file into a DataFrame in a single call; the first row is automatically treated as the column header.

Once loaded, rows can be filtered with boolean indexing: df[df["chromosome"] == "chr7"] produces a new DataFrame containing only the rows where that condition is true. .iterrows() then yields (index, Series) pairs for each row, where the Series allows column access by name. Individual values are returned as objects that may need explicit int() or float() casts — pandas uses its own numeric types and will raise a TypeError in some arithmetic contexts without the cast.

This is not the fastest pattern (fully vectorised operations are faster) but it is the clearest for the kind of per-row string formatting that every conversion function does here, where readability of the output format is the priority.

import pandas as pd

df  = pd.read_csv("target_region_cn.tsv", sep="\t")    # load TSV
sub = df[df["chromosome"] == "chr7"]              # filter to chr7

for _, row in sub.iterrows():                      # iterate filtered rows
    chrom  = row["chromosome"]
    start  = int(row["windowStart"])                 # explicit cast needed
    end    = int(row["windowEnd"])
    ratio  = float(row["windowTumorRatio"])
    lines.append(f"{chrom}\t{start}\t{end}\t{ratio:.4f}")
  • 1
    pd.read_csv(..., sep="\t") — reads the header row as column names; subsequent rows become data; the whole file is loaded into memory at once
  • 2
    df[df["chromosome"] == "chr7"] — boolean indexing; the inner expression produces a boolean Series; the outer brackets select only True rows; returns a view or copy of the DataFrame
  • 3
    for _, row in sub.iterrows(): — yields (integer_index, Series) pairs; the _ discards the row index which is not needed for BEDGraph output
  • 4
    int(row[...]) and float(row[...]) — explicit Python casts; pandas stores integers and floats in NumPy types that may cause type errors in f-string formatting or arithmetic without the conversion
In this file

Every one of the 9 conversion functions follows this exact pattern: load a DataFrame (already done in the Load phase), filter to a chromosome, iterate with .iterrows(), cast values, and append a formatted string to a list. The list is joined with "\n".join(lines) at the end to produce the final BEDGraph or SEG string.

09 tarfile, gzip, and BytesIO

PURPLE produces multiple output files (copy-number segments, target-region coverage, allele frequencies) that are bundled into a single .tar.gz archive for transfer. The Python standard library handles this entirely without unpacking to disk.

tarfile.open(path, "r:gz") opens a gzip-compressed tar file for reading. tf.getmembers() returns a list of TarInfo objects, each with a .name attribute (the path inside the archive). tf.extractfile(member) returns a file-like object; calling .read() on it yields raw bytes. Those bytes are passed to io.BytesIO(), which wraps them as an in-memory file object that pandas can read exactly as it would a real file — no temporary file is written to disk.

The BAF file adds a second complication: in production archives the member itself is also gzip-compressed (named .amber.baf.tsv.gz). The extracted bytes must first be passed through gzip.decompress() before being wrapped in BytesIO. This double-compression is the reason load_purple_data checks for the .gz-suffixed member before falling back to the plain .tsv path used in test fixtures.

import tarfile, gzip, io
import pandas as pd

with tarfile.open("purple_output.tar.gz", "r:gz") as tf:
    members = tf.getmembers()   # list of TarInfo objects

    # Plain TSV member — single gzip layer from the outer tar
    m      = next(m for m in members if m.name.endswith(".segment.tsv"))
    seg_df = pd.read_csv(io.BytesIO(tf.extractfile(m).read()), sep="\t")

    # Double-gzipped member — must decompress before wrapping
    bz     = next(m for m in members if m.name.endswith(".baf.tsv.gz"))
    raw    = gzip.decompress(tf.extractfile(bz).read())
    baf_df = pd.read_csv(io.BytesIO(raw), sep="\t")
  • 1
    "r:gz" — open mode: r = read, :gz = the outer file is gzip-compressed; the tar format is still used for directory structure inside
  • 2
    tf.getmembers() — returns a list of TarInfo objects; each has .name (path within archive), .size, and other metadata; no file data is extracted yet
  • 3
    io.BytesIO(tf.extractfile(m).read()) — extractfile returns a file-like object; .read() gives bytes; BytesIO wraps those bytes so pandas treats them as an open file handle
  • 4
    gzip.decompress(raw_bytes) — decompresses a gzipped payload back to raw bytes; required here because the BAF member inside the tar is itself a .gz file (two compression layers total)
In this file

load_purple_data() does all of the above to extract three TSVs from one archive. The function first searches for the double-compressed .amber.baf.tsv.gz member; if absent (e.g. in a test fixture) it falls back to a plain .amber.baf.tsv member read via the inner read_by_suffix() helper. The segment and CN files are always plain TSVs and use read_by_suffix() directly.

10 log₂ and the CN/ploidy transformation

Copy number is ratio data: a deletion, losing a copy, halves (0.5x) the signal, whereas a duplication, gaining a copy, increases it by 1.5x. On a linear scale this is asymmetric — a gain from 2 to 3 copies looks different to a deletion from 2 to 1. The log₂ transform makes gains and losses symmetric around 0, which is why almost all CN visualisation tools display log₂ ratios.

The specific formula is math.log2(CN / ploidy). Dividing by ploidy first normalises for tumour ploidy: a diploid genome has ploidy 2, so at CN = 2 the result is 0 (diploid baseline). At CN = 4 the result is +1 (one doubling above baseline). At CN = 1 the result is −1 (one halving). math.log2(x) raises ValueError for x ≤ 0, so every conversion function guards with if cn <= 0: continue before computing the log.

import math

cn, ploidy = 4.0, 2.0

if cn <= 0:
    continue            # guard: math.log2(0) raises ValueError

log2_r = math.log2(cn / ploidy)   # +1.0 → one doubling above diploid baseline

# Classify by threshold into one of five CN states:
# log2_r < -1.0          →  hodel   (homozygous deletion)
# -1.0 <= log2_r < -0.3  →  loss    (single-copy loss)
# -0.3 <= log2_r <  0.3  →  diploid (normal)
# 0.3  <= log2_r <  1.0  →  gain    (copy number gain)
# log2_r >= 1.0           →  amp     (amplification)

CN states in CN_STATES

State key log₂(CN/ploidy) range Colour Meaning
"hodel" < −1.0 #8b0000 dark red Homozygous deletion; both alleles lost
"loss" −1.0 to −0.3 #fca5a5 light red Single-copy loss; one allele deleted
"diploid" −0.3 to +0.3 #4d4d4d grey Normal copy number; near diploid baseline
"gain" +0.3 to +1.0 #93c4e0 light blue Copy number gain; one extra copy
"amp" ≥ +1.0 #08306b dark blue Amplification; high-level copy number increase

11 BEDGraph format

BEDGraph is a four-column tab-separated text format that associates a numeric value with a genomic interval. The four columns are: chromosome, chromStart, chromEnd, and value. Coordinates are 0-based half-open: a region covering base positions 1–1000 is written as start = 0, end = 1000 (the start is included, the end is excluded). This is the same convention as BED format.

igv.js treats BEDGraph data as a "wig" track (type: "wig", format: "bedgraph"). With graphType: "bar" it draws a bar chart, and with graphType: "points" it draws a scatter plot. The value column can be any floating-point number; negative values are drawn below the baseline.

# BEDGraph format: chrom   chromStart   chromEnd   value
# Coordinates are 0-based, half-open (start inclusive, end exclusive)
chr1    0          999         0.5123
chr1    999        2000       -0.2345
chr7    49999      50000       1.0000
chrX    1234567    1235000     0.0012
chr22   10000000   10500000   -1.5001
  • 1
    Column 1: chrom — chromosome name exactly as used in the genome reference (e.g. chr1, not 1); igv.js uses this for track-to-genome alignment
  • 2
    Columns 2–3: start and end — 0-based half-open; a single base at 1-based position P becomes start = P−1, end = P in BEDGraph — exactly the conversion applied to AMBER BAF positions
  • 3
    Column 4: value — any floating-point number; for CN log₂ tracks, 0.0 is the diploid baseline; negative values are rendered below the axis in igv.js bar tracks
In this file

Seven of the nine conversion functions return BEDGraph strings: coverage_log2_bedgraph, cn_bars_by_state (returns a dict of 5 strings), baf_bedgraph, baf_bedgraph_mirror, baf_seg_bars_by_state (returns a dict of 10 strings), cnr_to_bedgraph, and genemetrics_to_bedgraph. AMBER positions are 1-based, so the BAF functions convert with pos−1 as the start and pos as the end — writing a single-base BEDGraph interval for each BAF measurement.

12 SEG format

SEG (segmented copy number) is a six-column tab-separated format used to represent copy-number segments — contiguous genomic regions called as having the same copy number. Unlike BEDGraph, SEG includes a sample ID column and a probe count column, and is specifically designed for multi-sample copy-number data. The first row is always the header.

igv.js renders SEG data as a compact band track (type: "seg") with colour-scaled rectangles: blue shades for gains, red shades for losses. The Seg_Mean column holds the log₂ ratio used for the colour scale. A dot (.) is used as a placeholder for Num_Probes when the count is not available or not meaningful.

# SEG format — tab-separated, header row required
SampleID    Chromosome  Start     End       Num_Probes  Seg_Mean
SAMPLE01    chr1        1000000   5000000   .            0.8234
SAMPLE01    chr1        5000001   9000000   .           -0.5123
SAMPLE01    chr7        2000000   8000000   142          1.4501
SAMPLE01    chr17       7572000   7580000   .           -1.8034
  • 1
    SampleID — the sample name injected by the script; enables multi-sample SEG files; igv.js displays one row per sample in the track
  • 2
    Start and End — 1-based closed coordinates in the SEG convention (unlike the 0-based half-open BEDGraph coordinates)
  • 3
    Seg_Mean — the log₂(CN/ploidy) value; igv.js maps this to a blue–white–red colour scale via the posColorScale and negColorScale track options
In this file

to_seg() converts the PURPLE segment.tsv to a SEG string using the sample ID directly. cns_to_seg() converts CNVkit .call.cns segments and appends _cnvkit to the sample ID to distinguish the two tracks in the viewer. Both SEG strings are rendered in igv.js using type: "seg" tracks, which appear as narrow coloured bands below the bar chart track.

13 Python str.format() and {{ }} escaping

Python's str.format() method substitutes named values into a string template by finding {name} placeholders and replacing them with the corresponding keyword argument. The HTML template in this file is a ~130-line Python string that contains large amounts of JavaScript, and JavaScript syntax uses { and } everywhere — for object literals, arrow functions, template literals, and destructuring.

This creates a conflict: any bare { or } in the template string would be treated as the start of a format placeholder, causing a KeyError or ValueError. The solution is to double the braces: write {{ to produce a literal { in the output, and }} to produce a literal }. Python's format parser converts all {{ → { and }} → } after substituting real placeholders.

# Double braces {{ }} produce literal { } in the output
template = "igv.createBrowser(div, {{ genome: '{genome}', locus: '{locus}' }});"

filled = template.format(genome="hg38", locus="all")
print(filled)
# → igv.createBrowser(div, { genome: 'hg38', locus: 'all' });

# Extra keyword arguments that have no matching {placeholder}
# are silently ignored — no KeyError is raised:
template.format(genome="hg38", locus="all", extra="ignored")   # fine
  • 1
    {{ ... }} in template — each double brace is a single escape sequence; the entire JS object literal { genome: 'hg38' } must be written as {{ genome: 'hg38' }} in the Python string
  • 2
    {genome} is a real placeholder — a single-brace placeholder is replaced with the keyword argument value; it coexists with double-brace literals in the same string
  • 3
    Extra kwargs are silently ignored — str.format(**kwargs) only raises KeyError for missing arguments (a placeholder exists but no matching kwarg); unused kwargs are permitted
In this file

HTML_BARS is a ~130-line template string where every JavaScript object literal is written with {{ and }}. This includes the entire igv.createBrowser() call, all track configuration objects, all Blob() constructor arguments, and the colour scale objects. The 26 real placeholders — {sample}, {purity}, {cov_log2_bg}, etc. — are the only single-brace sequences. After str.format(**kwargs) runs, the output is valid JavaScript with normal {} braces throughout.

14 JavaScript blob URLs

A blob URL is a browser-local URI created by URL.createObjectURL(new Blob([data])). The browser allocates an in-memory object, assigns it a blob: scheme URI (e.g. blob:http://localhost/abc-123…), and makes it accessible as if it were a real network URL — but only within the current tab's session. Nothing is sent over the network; the data lives entirely in the browser's heap.

igv.js expects its track url: fields to be fetchable URLs. By passing a blob URL instead of a real HTTP URL, igv.js fetches the BEDGraph or SEG data from memory rather than a server. This is the mechanism that makes the output file fully self-contained: all 19 data strings (BEDGraph tracks and SEG strings) are embedded directly in the HTML as JavaScript template literals, converted to blob URLs at page load time, and passed to igv.js track configurations.

// Utility function defined at the top of the embedded <script>
function blob(txt) {
    return URL.createObjectURL(
        new Blob([txt], { type: "text/plain" })
    );
}

// Each data string is a JS template literal injected by Python str.format():
const barAmpBg = `{bar_amp_bg}`;   // placeholder filled by render_html()

// Passed to igv.js as if it were a real HTTP URL:
// { type: "wig", format: "bedgraph", url: blob(barAmpBg), ... }
  • 1
    new Blob([txt]) — creates an immutable binary object from the text string; type: "text/plain" sets the MIME type so igv.js correctly parses the content
  • 2
    URL.createObjectURL(blob) — registers the blob in the browser's object URL store and returns a unique blob: URI; this URI is valid only for the lifetime of the current page
  • 3
    Template literal injection — the backtick string `{bar_amp_bg}` in the HTML template becomes a JS string containing the full BEDGraph text after Python's str.format() fills in the placeholder
  • 4
    No server required — igv.js fetches from the blob URL via the browser's internal fetch mechanism; the HTML file can be opened directly from disk (file://) or from any web server; all data travels with the file
In this file

All 19 data strings — coverage log₂, 4 CN-state bar tracks, BAF top and bottom scatter, 8 fitted-BAF bar tracks (4 states × 2 arms), PURPLE SEG, CNVkit CNR scatter, CNVkit segment SEG, and CNVkit genemetrics — are injected as JS template literals and each is wrapped in the blob() helper before being passed to an igv.js track url: field. The blob() function itself is defined immediately above the igv.createBrowser() call in the HTML_BARS template. This is why opening the output HTML file in a browser requires only the igv.js CDN script; the entire copy-number dataset is embedded in the file.
